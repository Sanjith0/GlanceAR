# Glance acceptance flows

This repository started empty. The browser preview is a labelled sample-data walkthrough with real local hand inference, not evidence of native hardware or live audio/transcription operation.

## People matching and Connect Facebook acceptance inventory

Added November 12 on branch `facebook-people-matching`, from `events-discover-mode` at `7dc4930`. Two additions to the Events view: interests can come from a person's own Facebook account, and people at the same Glance event see what they have in common. No Glance flow below is replaced.

- **Connect Facebook (web build):** On Signals, with a backend and a registered profile, a button opens Facebook Login in a pop-up that asks for exactly `user_likes` and `user_posts`. After approval the backend exchanges the code, reads up to 200 liked Pages and up to 25 recent posts once, removes Glance's own access (`DELETE /me/permissions`), and then has `muse-spark-1.3` turn what it read into interests. They arrive as removable chips tagged FROM FACEBOOK, with a note saying how many Pages and posts were read and a second note confirming that access was removed.
- **Nothing from Facebook is kept:** The access token lives only inside that one backend action. Pages, posts, codes and tokens are never written to a table, a log or browser storage. Logs carry a failure code only.
- **Every way out is plain:** Cancelling on Facebook or in the app shows "Facebook sign-in was cancelled. Nothing was read." and frees the button. An empty account, a refused code exchange and a Muse failure each show a message and add no interests; access is still removed when Muse fails. If liked Pages are refused but posts are allowed, the posts alone are read. If Facebook does not confirm the removal, the interests still arrive with a note telling the person how to remove Glance themselves.
- **Where it is not offered:** The sample walkthrough has no backend, so the card says that instead of showing a button. The native app says sign-in is on the web build. Without a Glance profile the card asks for one first.
- **Events from Facebook data:** The Facebook interests feed the same `discover.recommend` ranking as every other signal. Reels, watch and browsing history are never read, because Facebook offers apps no permission for them; the "Your algorithm" screenshot remains the consented substitute.
- **People matching is opt-in:** The switch "Match me with people at events" on Signals is off by default. Switching it on saves the current interest list (at most 24) to the profile and keeps it in step with later edits. Switching it off deletes the list and that person's stored matches; the chips stay on the device.
- **In a Glance event:** Each other member who also opted in shows YOU'RE BOTH INTO with the shared interests in the viewer's own words and one question to open with, and whoever shares the most comes first. A status row carries the source tag, the viewer's interest count with an Edit link to Signals, and a refresh button. With matching off, a card explains the feature and links to Signals.
- **Muse does the matching:** `people.match` makes one `SharedPairs` call that pairs phrases across the lists (other members are sent as `p1`, `p2`, never by name or profile; a pair is kept only if both phrases really are in the two lists) and one `Openers` call that writes a question per person from the confirmed overlap only. The result is tagged MATCHED BY MUSE SPARK, stored per viewer and event, reused until a list changes, and deleted after 24 hours.
- **Honest fallback:** Until Muse has judged the current lists, when it fails, and at the daily cap (40 people-matching calls per profile per UTC day), the overlap is a wording match tagged BASIC MATCH with the reason and a plain opener. The sample walkthrough matches its two sample attendees on the device and tags the result SAMPLE MATCH. Neither is ever labelled as Muse.
- **LIVE Camera:** A recognized person's talking points lead with the same overlap and opener.
- **What another person can learn:** Only the overlap, in their own wording. Another member's phrasing, the rest of their list and its length never reach the viewer's device.
- **Claim boundaries and known gaps:** Real Facebook Login needs the builder's own Meta app, and until App Review only people with a role on that app can sign in. Any HTTPS origin is accepted as the return address, so the Meta app's Valid OAuth Redirect URIs list is the gate. Saving a list is not rate limited, so a member could probe another's list by re-saving guesses, and a judged, empty overlap hints that two lists have nothing in common. With a backend, a web session keeps its device credential in browser local storage (memory only in the sample walkthrough), so a closed tab cannot switch matching off and its saved list stays with the profile; anyone with access to that browser profile can act as the account until site data is cleared. Leaving out sensitive topics is an instruction to the model, not a filter. Not affiliated with or endorsed by Meta.

## Events view (Discover) acceptance inventory

Added November 11 on branch `events-discover-mode`, from `main` at `c809bee`. A switch in the header turns the whole app from the usual Glance UI into an Events UI in the style of Luma and Partiful, and back. None of the Glance flows below is replaced.

- **One switch, two faces:** `Glance | Events` sits in the first tab's header on both faces. Switching relabels the same three tabs (Events, Connections, You become Discover, Going, Signals) without navigating, reloading or dropping Glance state. The choice, signals, picks and RSVPs live in memory only, so a reload returns to the Glance face with nothing kept. No browser storage is introduced.
- **Discover:** A labelled sample catalog of 20 fictional Dallas–Fort Worth events in eight categories, dated on a rolling two-week window. Search (title, venue, host, category, tags) and single-choice category chips filter the list and the picks together; an empty result says so.
- **Signals the person chooses:** Typed interests, the existing Glance intro (with an off switch), sample signals (tagged SAMPLE), or interests that Muse Spark reads from a screenshot of Facebook's "Your algorithm" topics (tagged FROM SCREENSHOT). Every interest appears as a removable chip before it is used. The app never claims to read Reels or watch history: the copy states that Facebook does not offer that to apps.
- **Muse ranking:** With a backend and a registered profile, `discover.recommend` asks `muse-spark-1.3` through Meta's chat completions API for up to six picks, each with a score and a one-line reason, under a strict JSON schema. Events outside the catalog, duplicates and malformed rows are dropped. The row is tagged RANKED BY MUSE SPARK and the event page names the model.
- **Honest fallback:** In the sample walkthrough (no backend), without a profile, or when Meta fails, picks come from a whole-word keyword match tagged BASIC MATCH, with a notice that says why. A fallback is never labelled as Muse.
- **Screenshot read:** `discover.readScreenshot` sends one JPEG, PNG or WebP data URL (checked by its leading bytes, at most 2,000,000 characters) as an `image_url` part of the user message. It has no offline stand-in: a failure shows a provider-free error and adds no interests.
- **Privacy and cost:** Signals, picks and RSVPs are never written to the database and the screenshot is not stored. The only new stored data is a per-profile daily counter (`discoverUsage`, 40 Muse-backed calls per UTC day). Both actions require a registered device credential. Logs carry a failure code only, never interests, images, keys or provider bodies. Superseded in part on November 12: once a person switches people matching on, their interest list is saved with their profile until they switch it off (see the inventory above).
- **Event page and plans:** Cover, time, host, venue, attendance, price, "Why this fits you" with its ranking source, About, tags, and I'm going / Interested (tap again to undo). The Going tab lists both groups. RSVPs are local to the session and are not sent to a host.
- **Bridge to Glance:** "Open a Glance room" creates a normal Glance event named after the sample event, returns to the Glance face and opens it. The same event then offers "Open your Glance room".
- **Claim boundaries:** Sample events, not real listings. No Facebook Login, Graph API, Reels, watch-history or account data is read. Not affiliated with or endorsed by Meta. Superseded in part on November 12: Connect Facebook now reads liked Pages and recent posts through Facebook Login when the person asks it to; Reels, watch and browsing history are still never read.

## Three-second LIVE Camera revision acceptance inventory

Baseline inspected in the browser on October 25 on `main` at `722bff4`: the LIVE Camera page shows the face database and video window, but no countdown. Its demo sighting shortcut simulates a reciprocal recognition after 1.5 seconds and automatically routes any active conversation. This revision is limited to the laptop/browser demo's camera-to-conversation transition; live authenticated reciprocal sightings and the existing hand-finish/capture pipeline are not being replaced.

- **Continuous local co-visibility:** Enroll the current demo participant and one enabled event peer. Exactly those two distinct, registered participants must be recognized in the same camera view for at least three continuous seconds. A lone peer must never simulate a second device's recognition.
- **Visible countdown:** Show 3, 2, 1 with a readable hold instruction and progress. During the last 2.5 seconds only the 4:3 camera window pulses green (two pulses per second, steady under Reduce Motion) with "Initiating conversation" and "Connection building…"; losing either face stops it immediately. Keep the camera, names and talking points present throughout the hold; do not route before a fresh qualifying frame after the full three seconds.
- **Reset, not pause:** A missing, unknown, duplicate, extra or changed participant resets the hold. So do a scan/rescan/delete, event/actor/permission change, loss of focus, hidden/page-hidden tab, camera switch/error/end, or a stale inference gap. A display timer may expire progress but never create a conversation.
- **No stale-frame completion:** Drop repeated video frames and late inference results. The final qualifying frame must have been sampled after the three-second deadline, not merely delivered late; a frozen camera or stalled model cannot satisfy the hold.
- **Scoped single transition:** A successful hold creates one demo conversation and transfers the existing camera directly to “Three fingers. You’re connected.” An already-active conversation must not auto-route around the countdown; it may offer an explicitly labelled resume action. A stale asynchronous pairing result must not navigate a different event or unfocused screen.
- **Preserved experience:** Keep consented in-memory enrollment, profile talking points, the live backend's independent reciprocal-sighting contract, video-only camera ownership, exact-destination handoff, real hand detection, authoritative green acknowledgment, same-route chat and all existing capture/navigation barriers.
- **Actual-model evidence:** Use the repository's fictional sample portraits, normal enrollment controls and a prerecorded fake-camera stream with the actual production face model. Verify a short two-face hold followed by absence resets without routing, then a fresh full hold visibly counts down and routes once. Do not use the user's uploaded photograph, injected descriptors or a mocked matching result for this signoff.
- **Regression and layout:** Replay the surrounding flows below after the final export. Inspect waiting, counting, interrupted and transition states at phone and desktop sizes, including short windows; confirm no clipped countdown, unreadable labels, unexpected microphone request or horizontal overflow.
- **Claim boundaries:** Same-camera demo co-visibility is not two-device mutual authentication, liveness, real-room recognition accuracy, native compilation or actual audio transcription. The private hosted preview's camera restriction remains explicit; localhost camera proof and hosted fallback checks stay separate.

## Existing flows to preserve

- Events: create an event, validate empty title, join with a valid invitation, reject invalid invitations, open attendee list.
- Enrollment: a live device requires a name and portrait, permission failures produce readable errors, no hidden camera access.
- Event entry: one clearly disclosed event permission enables recording and gesture-triggered sharing. A portrait or membership alone never enables real capture. Each account changes only its own permission; disabling it stops unfinished sessions.
- Event defaults: newly created events begin with permission off and no other attendees. Preview copy must not claim both attendees already enabled Glance in an empty or paused event.
- Encounter: entering an event never starts or opens a conversation by itself; the event screen stays put. Encounters start from LIVE Camera's 3-2-1 hold or the labelled Simulate next encounter control, with no per-conversation approval or Start button. An already-active conversation is still reopened. Selecting an enabled profile remains the live fallback.
- LIVE Camera: shown only once Glance is enabled for the event. Opens video only (never audio); ordinary leaving, hidden tabs and lost focus close it. The exact conversation route can inherit the stream through a fixed 1.5-second handoff, without an event-screen bounce or a second camera acquisition. Existing matching is unchanged: scanned attendees get a box, name and profile-derived talking points, your own scan is "You", and unscanned faces are "Not registered". The preview requires a fresh three-second same-camera hold of yourself and one enrolled peer; live mode retains authenticated reciprocal sightings.
- Preview summaries (only with `EXPO_PUBLIC_DEMO_SUMMARY_URL` and a backend with `GLANCE_DEMO_SUMMARIES=enabled`): the browser microphone records from conversation start to finish, with a red indicator. Finish uploads one 16 kHz mono WAV; the chat opens with "Your recap is on its way", then shows the AI summary, topics and next steps, with the Speaker 1 / Speaker 2 transcript behind **Show transcript**. Stop without sharing, cancel and leaving upload nothing and release the microphone; a provider failure shows a safe error and keeps the chat. Without the URL, the labelled sample recap is unchanged.
- Face scans: separate from the portrait and gated by an explicit consent box; a guided scan (three consistent straight-on samples, then up to eight more as the head moves around a ring, plus up to three made to look distant); a face that already matches another attendee is refused. Live mode scans only your own face; the preview may scan up to five attendees, held in memory only. Delete is always available and withdraws pending sightings.
- Face directory: withheld unless the viewer enabled Glance; contains only enabled members with a scan; updates reactively on join, enable, pause, rescan and delete.
- Consent: new event-mode conversations inherit both accounts' standing event permissions. Older backend clients remain compatible, but the new UI does not present per-conversation approval forms.
- Capture: web never opens a microphone; native starts only after server authorization, with a native expiring lease; either person has Stop.
- Gesture: an authorized finish signal closes capture and connects using the two event permissions. It is not biometric proof of two identities. Ordinary Stop, interruption and loss of permission do not connect or share.
- Sharing: a confirmed gesture finish displays one brief green acknowledgment with the video still live, then opens the shared chat on the same route, without a Make it mutual / Confirm connection screen. A sees B's portrait and B sees A's, with the same recap; sample content remains labelled.
- Chat: empty drafts cannot send, whitespace is trimmed, sent messages appear for both participant views, no automatic fake replies appear, and deletion requires an explicit destructive confirmation.
- Next conversation: return to an enabled event, simulate the next encounter, and verify a new conversation segment with its own messages/recap rather than overwriting the previous one.
- Sensor setup: native microphone/camera permission requests occur at event activation before an automatic capture attempt. Web sample mode never requests microphone access.
- Capture ownership: the choice is frozen before pairing, persisted on the conversation, and locked while any recorder session is active. A glasses-owned recorder companion sends no presence acknowledgements or phone-audio calls; phone-owned conversations are read-only in the harness.
- Private handoff: revealing setup and copying the complete JSON are separate deliberate actions. Native copy is foreground-only, local-only and expires after 60 seconds; tokens never enter deep links or query parameters. Native clipboard behavior still needs device verification.
- Failure: backend unavailable, upload failed, expired lease, permission denied, unavailable native module, and failed AI processing have explicit states.
- Deletion: cancel erases the pending local recording; delete hides the shared record for both participants after confirmation.
- Navigation: events, connections, profile, event detail, conversation and shared chat; no dead links or horizontal overflow at 375px and desktop. Keep the conversation route mounted through finish/upload. Unsafe local work blocks route removal and native swipe; confirmed discard must await native stop acknowledgement before allowing navigation, without deleting an already-connected chat.
- Hardware: iOS compile, install, actual PCM output, microphone routing, camera concurrency, background stop, native watchdog and Adventurer DAT capability require real device verification.
